Two frictions hit on 2026-09-26 in beliefs, where python/.venv is a work-link into WORK_ROOT storage whose external directory had been deleted. (1) The dangling link surfaced only as uv's 'failed to create directory python/.venv: File exists (os error 17)' inside the pre-push hook; nothing named the link or the fix (work-link <repo> converge materializes it). A cheap detector would have saved the diagnosis: e.g. work-link --check (exit non-zero listing dangling managed links) that just setup or a hook preflight can call, or converge reporting 'dangling' distinctly. (2) work-link --ensure .venv run from beliefs/python/ created beliefs/.venv -> WORK_ROOT/beliefs/.venv at the repository root, not python/.venv: NAME resolves against the repo root regardless of cwd, silently. Either resolve NAME relative to the cwd, or refuse a NAME that does not exist at the root when the cwd is a subdirectory. Also worth a line in the usage text: <root>/../.dropbox-work resolves to WORK_ROOT, so the directories there are link targets, not residue.
